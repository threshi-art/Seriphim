# Ei@raM and Seraphim Comparative GitHub Landscape

## Purpose

Use this skill to identify what is genuinely novel in a proposed governed agent or intelligence architecture and what is established open-source practice. Compare components and operating models—not names, branding, or AGI claims.

Read `references/comparison-catalog.md` for a curated starting set of public projects.

## Comparison Workflow

1. **Extract the system claim.** Separate personal workspace, memory, agent execution, tool governance, evidence/provenance, intelligence fusion, policy control, simulation, and self-improvement into independently testable capabilities.
2. **Search by architectural slice.** Search separate categories: personal command centers; agent orchestration and controls; OSINT or threat-intelligence fusion; data/AI provenance; causal or scenario models; and evaluation-gated improvement.
3. **Verify primary sources.** Open the repositories directly. Record documented scope, license, maintenance signals, architecture, and integrations. Do not rely only on GitHub search snippets.
4. **Compare capability boundaries.** For each candidate, state: what it demonstrably implements, what it lacks, and one transferable architectural lesson. Distinguish production subsystem maturity from research prototypes.
5. **Synthesize conservatively.** Answer whether the *complete combination* is public and credible. A project that has memory, agents, or a graph does not thereby demonstrate general intelligence, autonomous strategic reasoning, or safe high-impact decision support.
6. **Recommend composition, not wholesale adoption.** Select narrow patterns that fit the intended stack. Preserve domain boundaries, policy controls, human approval, auditability, and evaluation gates.

## Required Output

Provide an executive answer, a comparison table, top three closest analogues, the differentiating integration contract, transferable patterns, explicit non-equivalences, and source links. Cite every technical assertion with the relevant repository or official documentation.

## Comparison Rules

| Rule | Apply this standard |
|---|---|
| Compare structure | Assess architecture, state model, tool boundary, governance, and operations rather than model marketing. |
| Separate evidence from claims | Treat a project README as evidence of documented capability, not proof of correctness or broad real-world reliability. |
| Name limits clearly | State missing privacy, authority, provenance, evaluation, or human-approval controls plainly. |
| Preserve data boundaries | Never recommend indiscriminate convergence of cyber, OSINT, personal, behavioral, or sensitive records. |
| Reject AGI inflation | Never call a system AGI solely because it uses agents, memory, tools, graphs, or self-modification. |

## Safety Boundary

Do not use this skill to recommend autonomous diagnosis, profiling, targeting, or high-impact external action. Frame all high-impact use cases as governed decision support with explicit authority, data governance, uncertainty, and accountable human review.
